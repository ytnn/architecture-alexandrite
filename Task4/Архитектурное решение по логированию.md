# Архитектурное решение по логированию

## 0. Анализ системы компании и C4-диаграммы в контексте планирования логирования
Требуется сбор логов из систем: CRM API, MES API, Shop API, RabbitMQ, MES, т.к.эти системы влияют на обработку заказа.

Shop API
- Изменение статуса заказа: логируем время, идентификатор покупателя, номер заказа
- Создание нового заказа: логируем время, идентификатор покупателя, номер заказа

RabbitMQ:
- Отправка сообщения в брокер: логируем время, имя очереди

MES API:
- Получение заказа в расчет: логируем время, номер заказа
- Изменение статуса заказа: логируем время, номер заказа, статус

CRM API:
- Получение команд от оператора: логируем время, номер заказа, тип команды
- Получение сообщений от MES: логируем время, номер заказа, тип сообщения

MES:
- Начало обработки заказа: логируем время, номер заказа
- Изменение статуса заказа: логируем время, номер заказа, статус

Использование других уровней логирования:

- TRACE/DEBUG - на тестовых контурах, при поиске сложных ошибок на прод
- WARN - для логирования некритичных ошибок и прочих предупреждений
- ERROR - для логирования критичных ошибок и необработанных исключений

## 1. Мотивация
Логирование сильно повышает обнаружение ошибок и других проблем в работе системы. Это приведет к сокращению необработанных заказов, оптимизации и ускорению работы приложения, что увеличит удовлетворенность клиентов, повысит продажи и увеличит прибылть компании. 
В случае если ресурсов на внедрения логирования и трейсов не достаточно, необходимо подключить логи и трейсы в MES API, MES и RabbitMQ, т.к. непонятно теряются ли заказы или некорректно приоритезируются. Потом подключить логирование в SHop API для логирования данных по заказам.

Внедрение рейсинга повлияет на слежущие метрики:
* Время ответа для ключевых API: Shop, MES, CRM
* Количество ошибок ERROR
* Время обнаружение и решение инцидента
* Количество инцидентов, которые аффектят на клиентов компании
* Время недоступности сервиса


## 2. Предлагаемое решение
Внедряем ELK: добавляем логирование во все подсистемы, данные отправляются в LogStash, индексируются в ElastikSearch и визуализируются с помощью Kibana. В Kibane настраиваем дашики для удобного отображения данных по новым заказам, ошибкам, расчетам в MES. [Схема](https://raw.githubusercontent.com/ytnn/architecture-alexandrite/refs/heads/dev/Task4/%D0%90%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%BD%D0%BE%D0%B5%20%D1%80%D0%B5%D1%88%D0%B5%D0%BD%D0%B8%D0%B5%20%D0%BF%D0%BE%20%D0%BB%D0%BE%D0%B3%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8E.drawio)

**Аспекты хранения логов:**

Логи хранятся 30 дней для прод окружения, срок может меняться в ту или иную сторону в зависимости от бизнес-требований и возникших инцидентов. По умолчанию на проде включен уровень INFO, который можно расширять при возникновении инцидентов, с последующим возвратом в INFO. На тестовых средах срок хранения логов три дня, уровень - TRACE/DEBUG.
Используюься раздельные индексы для каждого сервиса.

**Аспекты безопасности:**
* Доступ в Kibanu только из внутренней сети компании или через VPN удаленно. 
* Каждый пользователь авторизован в системе и имеет определенную роль в Active Directory, ограниченную правами доступа чтения/записи. 
* Конфиденциальные данные не логируются.


## 3. Необходимые мероприятия для превращения системы сбора логов в систему анализа логов
Можно настроить алертинг:
- На резкое повышение количества ошибок
- На резкий рост или отмену заказов
- На резкий росто количества предупреждений
- Больщое количество авторизаций с одного IP
- Больщое количество неуспешных авторизаций
