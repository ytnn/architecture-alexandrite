# Архитектурное решение по кэшированию

## 0. Анализ системы компании и C4-диаграммы в контексте планирования кэширования
Произведя анализ системы пришел к выводу что кэшировать нужно разве что какие-то статичекие справочные данные из БД, поскольку заказы и их метаданные меняеются, постоянно приходят новые заказы и обновляются их статусы. При этом количество заказов и их метаданные наврядли представляют собой большой объем данных. Расчет стиомости по конкретным моделям можно просто сохранять в БД. Для интернет-магазина и CRM имеет смысл кэщировать статический контент: скрипты, картинки.

## 1. Мотивация
Внедрение кеширования в систему MES нужно для ускорения работы операторов и снижения нагрузки на серверы. Основные задачи кеширования:

-Ускорение отклика интерфейса при работе с заказами

-Снижение нагрузки на базу данных при частых запросах

-Повышение стабильности работы при пиковых нагрузках

## 2. Предлагаемое решение
Буду применять серверное кэширование в Shop API и MES API. Буду кэщировать справочные данные из БД для снижения нагрузки на них. Использую паттерн Cache-Aside из-за своей простоты и кэшировании только запращиваемых данных. Write-Through не подходит из-за обновления кэша при повторной записи. Refresh-Ahead не использую из-за его сложности и избыточности.

Sequence diagram

@startuml
actor User

participant "Shop API" as Shop
participant "MES API" as MES
participant "Redis Cache (MES)" as MESCache
participant "Redis Cache (Shop)" as ShopCache
database "MES DB" as MESDB
database "Shop DB" as ShopDB

== Операция: Получение списка заказов ==
User -> Shop : Запрос списка заказов
Shop -> ShopDB : Получение списка заказов
ShopDB --> Shop : Возврат списка заказов
Shop --> User : Возврат списка заказов

== Операция: Изменение статуса заказа ==
User -> Shop : Изменение статуса заказа
Shop -> ShopDB : Обновление записи заказа
ShopDB --> Shop : Подтверждение обновления
Shop --> User : Статус обновлен

== Операция: Получение справочных данных Shop ==
User -> Shop : Запрос справочных данных
Shop -> ShopCache : Проверка данных в кэше
alt Данные есть в кэше
    ShopCache --> Shop : Возврат справочных данных
else Данных нет в кэше
    Shop -> ShopDB : Получение справочных данных
    ShopDB --> Shop : Возврат данных
    Shop -> ShopCache : Сохранение данных в кэше
    ShopCache --> Shop : Подтверждение записи
end
Shop --> User : Возврат справочных данных

== Операция: Расчет параметров производства ==
User -> MES : Запрос расчета (например, стоимость или время производства)
MES -> MESCache : Проверка наличия данных в кэше
alt Данные есть в кэше
    MESCache --> MES : Возврат справочных данных
else Данных нет в кэше
    MES -> MESDB : Получение справочных данных
    MESDB --> MES : Возврат данных
    MES -> MESCache : Сохранение данных в кэше
    MESCache --> MES : Подтверждение записи
end
MES --> User : Возврат результата расчета
@enduml

Стратегия инвалидации кеша

Основная стратегия: по времени (Time-based TTL).

Кеш обновляется автоматически через заданный промежуток 5-30 минут.

Простая и надёжная схема, не требует сложных механизмов, идеально подходит для редко изменяющихся данных.

| Стратегия       | Преимущества                           | Недостатки                                    |
| --------------- | -------------------------------------- | --------------------------------------------- |
| Временная (TTL) | Простая, регулярно обновляет данные    | Может вернуть устаревшие данные в течение TTL |
| По ключу        | Точная актуализация конкретных записей | Сложнее в реализации, нужно управлять ключами |
| Программная     | Гибкость и контроль над инвалидацией кеша в соответствии с логикой и потребностями приложения| Высокая сложность и поддержка                 |
